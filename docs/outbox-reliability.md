# 申請保存・再送の安全性修正（0.4.9）

## 対象と作業境界

v0.4.8の元ソースを基準に修正し、公開版は0.4.9とする。API接続先、対象ホスト、権限、更新URL、難易度体系、3種の申請、右クリック・Shift右クリックは維持する。配布用ファイルは既存ビルドから生成する。初回のローカル検証完了後、管理者の追加承認に基づき公開・push・デプロイを行う。本番APIの試験投稿、実保存データの操作、Spreadsheetのデータ変更も行わない。

既存のゲートウェイ署名検証、投稿制限、4種類の旧GATEWAY拒否の復旧処理を保持する。旧版の問題を再現するスクリプトは合格判定には使わない。

## P0：個別の異常と保存領域の障害を分離

- `list()`は正常に読める自分の提案の配列という既存契約を維持。`inspect()`を追加し、正常一覧・要確認理由・所有者不明件数・先頭待機情報を取得する。
- キー、entry、metadata、payload、state、receipt、取消記録、versionを検証。個別異常は原本を残して隔離し、正常分の保存・送信を継続する。ID指定送信も同じ検証を通る。
- `keys()`や必要な`get()`の例外は保存領域へのアクセス障害として中断する。0件や送信成功へ変換せず、直接POSTへ迂回しない。
- 保存構造の読取と現在の受付条件を分離する。旧レベル等を含む提案は個別に要確認とし、payloadを補正しない。保存形式はv1を維持し、移行処理や自動初期化は導入しない。
- 正しい受領記録を優先する。state破損時にattemptsを0へ戻さず、受領記録がなければ要確認。未知versionも自動解釈しない。
- 自分の正常・異常原本を`records`付きの控えへ出力する。NaNや循環等の非JSON値は`structured-graph-v1`という明示的な出力表現を使い、黙ってnullに置換しない。これは控えの表現であり、保存形式の移行ではない。控えの自動インポートは実装しない。
- 他プレイヤーの内容は表示・送信・通常エクスポートから除外する。所有者不明・別所有者を示す異常原本は保存領域に残し、除外したことを明記する。所有者の手動確認が必要であり、自動削除しない。

## P1：再送・競合・取消・上限

- 同一実行環境では保存操作を直列化。Web Locks利用時はenqueue/send/flush/removeで同じロック名を使う。GM値の読み書きを原子的ロックとは扱わない。
- Web Locksはページの保存領域／オリジンに依存する。GMストレージが共有されても、`bms-ir.org`と`www.bms-ir.org`のロックまで共有されるとは保証できない。ロック不可・別ロック領域では通信の重複や、同内容・別IDの同時保存が残りうる。サーバー側の同一ID重複排除と区別する。
- 本番エントリーポイントでは全GM保存領域を覆うロックを確認できないため、未送信取消を安全側で無効化し、理由を表示する。検証済みの共有範囲を明示した環境だけ取消可。送信が先に進んだ場合、取消操作を控え削除へ読み替えない。
- 送信結果未確定の提案は取消不可。完了控えは1件ごとに対象・件数・サーバー上の撤回ではないことを確認して削除する。取消痕跡は保持し、自動整理しない。
- 未解決上限200件を維持し、送信済み・受付不可の控えや要確認データと分離。控えの自動削除は導入しない。
- この上限判定・同内容保存の直列化は共有ロックの範囲内の保証。別ロック領域から同時保存される場合、GMストレージだけでは件数判定や同一IDへの競合書込も原子的に保証できない。既知の既存IDの異内容は拒否するが、全環境の競合がなくなったとは説明しない。
- request_id、client_version、提案値等は保存後に書き換えない。同一IDの異内容を競合拒否し、同内容の保存済み提案を再利用する。再通信は同じpayload・IDで行う。

### サーバー側の照合

`submitApplication_()`のScriptLockが重複照合から受付作成までを覆うことをローカルの割込みテストで確認する。受付後の応答喪失、受領記録保存失敗、同一IDの異内容をテストする。

新規受付時にはP列request_idセルのノートに元の正規化済みpayloadのハッシュを保存し、`SpreadsheetApp.flush()`後に従来のRAW行書込を行う。ノート保存・flush失敗時は行を受け付けない。行書込失敗時に残る未使用行のノートは次の受付で再利用できる。A:Sの列構造とRAW値書込を維持し、無関係なノート文は保持する。

これにより、新規譜面のF/Gセルを管理者が修正しても、元payloadの再送は重複受付済みになり、異内容は拒否される。元データや編集済みF/Gは上書きしない。

**旧受付行の限界：** 照合ハッシュのない既存行は従来のセル比較を維持し、自動バックフィルしない。そのF/G等が既に編集されている場合、元内容を復元して照合する保証はない。ハッシュの未知形式・破損は安全側で競合拒否する。複製等でノートが失われた行も旧行と同じ制約を持つ。

サーバーの保証は同一request_idについてのもの。同内容・別IDの意図した再提案を永久禁止する規則は追加しない。ローカルのGAS模擬環境／Worker統合試験は、実Google環境での同時実行や永続化を検証したものではない。投稿者の実BMS-IR認証まで証明するものでもない。

## P1：HTTPと待機

- 非2xxでも妥当な`ok:false`エラーJSONは解釈する。HTTP 200＋エラーも維持。非2xx＋`ok:true`は成功扱いしない。
- 429はHTML等でも頻度制限と認識する。本文のミリ秒とRetry-Afterの秒／HTTP日時を区別し、妥当な値が複数あれば最大を採用する。欠落・不正時の429は10分、最小待機は30秒。正当な長い待機を10分へ切り詰めない。
- 明示的な待機期限は保存し、手動再送でも迂回しない。LOCK_TIMEOUTの内部再試行も本文の待機より早く行わない。
- 受付停止・通信障害・頻度制限と、設定確認・対応版確認が必要な保留を区別する。未知エラーは勝手に成功・完了とせず手動再開待ちにする。

## P2：表示と読み込み

- ページ構造不一致・MD5不一致・ログアウトを短く表示する。新旧DOM、一意性、URL/ranking_key/hash三者一致の解析条件は緩めない。
- 保存一覧に正常／要確認件数、理由、次の試行時刻、自動再送か手動再開か、先頭を待つFIFOの理由を表示する。申請受付と難易度表への承認・反映は区別する。
- 登録済み120秒／未登録30秒のlookupキャッシュは維持し、受付成功後にexistsや現在難易度を捏造しない。
- flushは有効な受領記録を持つ完了控えの可変stateを読まず、完了200件で値取得400回＋キー一覧1回に削減（元実装800回＋1回）。一覧・原本出力ではstateも検査する。永続索引や独立キャッシュは導入せず、毎回キーを読み直す。実ブラウザの速度測定ではない。

## 検証方法と未検証範囲

既存の`npm test`に`outbox-safety`、`outbox-concurrency`、`api-response-retry`、`server-idempotency`の合格条件テストを追加。メモリ内GMストレージ、独立した実行環境／ロック管理、固定時計、模擬HTTP、jsdom、GASのVMハーネス、外向き通信を差し替えたローカルWorker/SQLiteを使う。

実Firefox＋Tampermonkeyの複数タブ／両ホスト、実GM保存容量・権限、Google本番の同時実行と保存、実ユーザー申請は未実施。コードの反映確認と、実ユーザー申請の成功確認は分けて扱う。

実行コマンド：`npm test`、`npm run build`、既存接続先を維持した`npm run build:public`、`npm run smoke`、模擬URLでの`npm run build:test`と`npm run smoke:test`、`npm run test:gateway`。いずれも本番APIへの通信を必要としない。

2026/10/30の最終ローカル結果：unit 263件、生成物smoke 6件、test版smoke 1件、Worker/SQLite 11件が成功。build、build:public、build:test、checkおよび差分の空白検査も成功。実ブラウザ・本番環境の検証結果へ拡大解釈しない。
